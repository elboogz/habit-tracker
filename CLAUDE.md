## Commands

- `npx expo start` — start the Metro dev server (scan the QR with Expo Go, or press `i`/`a`/`w` for simulator/emulator/web)
- `npm run ios` / `npm run android` / `npm run web` — start the dev server targeting a specific platform
- `npm run lint` — run ESLint via `expo lint` (flat config in [eslint.config.js](eslint.config.js), extends `eslint-config-expo`)
- `npm test` — run the Jest (`jest-expo` preset) suite; currently pure-function tests under `lib/domain/*.test.ts` plus a generator test, no component tests yet
- `npm run build:edge-functions` — regenerate the shared-domain block inside both `supabase/functions/*/index.ts` from `lib/domain/` (see [scripts/build-edge-functions.js](scripts/build-edge-functions.js)); run this after changing `lib/domain/day-key.ts` or `lib/domain/habit-stats.ts`, then paste the regenerated file(s) into the Supabase Dashboard
- `npm run reset-project` — moves the current `app/`, `components/`, `hooks/`, `constants/`, `scripts/` to `app-example/` and scaffolds a blank `app/` (one-way; only run if explicitly asked to wipe the starter code)

## Architecture

This is a **habit-tracking app** built around a deliberate app-design framework: a core function (create/track habits), a core loop (log → instant reward), a 3-day starter challenge, accessory features (history, consistency charts, multiple habit types), a hard cap on screen count, and a retention hook (ongoing challenges + daily local reminders). It uses **file-based routing via Expo Router** (`expo-router/entry` is the app entry point in [package.json](package.json)). Routes are defined by the file structure under `app/`:

- [app/_layout.tsx](app/_layout.tsx) — root layout; wraps everything in `AuthProvider` then `HabitStoreProvider` and React Navigation's `ThemeProvider` (light/dark), registers the global notification handler, and defines the top-level `Stack`. Uses `<Stack.Protected guard={...}>` to route signed-out users to `sign-in`, then first-time users to `onboarding`, then everyone else to `(tabs)` — gated on `initializing`/`hydrated` so returning users never see a sign-in or onboarding flash. `unstable_settings.anchor` points to `(tabs)`.
- [app/sign-in.tsx](app/sign-in.tsx) — email/password sign in & sign up screen (Supabase Auth), toggles between modes, errors surfaced via `alertMessage`.
- `app/(tabs)/` — bottom `Tabs` navigator ([app/(tabs)/_layout.tsx](app/(tabs)/_layout.tsx)) with exactly **4 tabs**: `index` (Today — the core loop, shows today's date and lets you check/uncheck habits), `progress` (Behaviour Snapshot: a Momentum State badge + one-line narrative and Recovery Rate/Recovery Time per habit, an aggregate Total Completions/Consistency summary, the AI Coach card, and a toggle between "Last 14 days" and "Last 7 days" for the per-habit heatmaps), `challenges` (any number of concurrent active challenges, each over its own set of habits, past challenges, and the start-a-new-challenge flow), `settings` (reminder scheduling + a `__DEV__`-only developer tools section).
- [app/habit-form.tsx](app/habit-form.tsx) — modal route for creating/editing a habit (name, 3×5 emoji grid, type — "Daily" or "Count-based" — target, per-habit reminder times, and a "Delete habit" action when editing). Pass `?id=<habitId>` to edit.
- [app/habit/[id].tsx](app/habit/[id].tsx) — stack-pushed "Habit History" screen. Total Completions leads as a full-width card (Phase 3's cumulative, never-resetting anchor metric); Current + Best streak are folded into one supporting tile beside it (plain text, e.g. "Current: 0 · Best: 21", never a warning colour); a Recovery tile shows Recovery Rate or Recovery Time (whichever the habit's own display rules allow, omitted entirely if neither); a Consistency tile keeps the existing 28-day percentage. Below that, a calendar-grid view of the last 28 days via [components/habit-calendar.tsx](components/habit-calendar.tsx), and recent log entries with an emoji per row.
- [app/onboarding.tsx](app/onboarding.tsx) — first-run flow gated by `state.hasOnboarded`: welcome → "how it works" explainer (create/track, milestones & kickstarts, progress, reminders) → pick a habit → frame it as a 3-day challenge (started via `startChallenge([habit.id], 3)`) → opt into reminders. Re-triggerable from Settings dev tools via `resetOnboarding`.

Together that's **8 screens** — 4 tabs carry daily navigation, the other 4 (sign-in, habit form, habit detail, onboarding) are infrequent auth/modal/drill-in/once-only flows, keeping the *felt* surface area close to the 5-7 screen design constraint.

### Data layer & the core loop

- [lib/habit-types.ts](lib/habit-types.ts) — `Habit`, `HabitLog`, `Challenge`, `HabitState` types. Habits are `'simple'` (yes/no) or `'count'` (target reps per day, e.g. "drink water ×8"); completion is always derived from `HabitLog` entries, never stored as a flag. `Habit.reminderTimes?: string[]` holds optional per-habit `'HH:mm'` reminder times. `Challenge.habitIds: string[]` — a challenge covers a *set* of habits, not a single one. `HabitState.soundEnabled: boolean` gates the chime in `useCelebration`. `EMOJI_CHOICES` has 15 entries (a 3×5 grid in the habit form). `Habit`/`HabitLog`/`Challenge` all carry `updatedAt: string` (ISO timestamp), used for last-write-wins merging in the Supabase sync layer below.
- [lib/habit-store.tsx](lib/habit-store.tsx) — `HabitStoreProvider` / `useHabitStore()`: a Context + `useReducer` store, **local-first**: every mutation lands in the reducer (and `AsyncStorage`) instantly, with Supabase sync happening in the background — none of the mutators below know Supabase exists. The `AsyncStorage` key is scoped per signed-in user (`habit-tracker/state-v1:<userId>`, read via `useAuth()`); on the first hydration for a brand-new account with no scoped key yet, it adopts any pre-existing pre-auth data from the legacy unscoped key (`habit-tracker/state-v1`) rather than discarding it, uploads it once, then deletes the legacy key. All mutations (`addHabit`, `updateHabit`, `deleteHabit`, `logHabit`, `unlogHabit`, `startChallenge`, `setNotifications`, `setSoundEnabled`, `setChallengeStatus`, etc.) go through this. `unlogHabit(habitId)` removes the most-recently-logged entry for that habit today (LIFO), powering the "uncheck" interaction on Today. `startChallenge(habitIds, durationDays)` no-ops if `habitIds` is empty or any of those habits already belong to an active challenge — **multiple challenges can be active at once, but a given habit can only be in one active challenge at a time** (a challenge day only counts if every included habit was done, so overlapping habits between two active challenges would be ambiguous). `resetOnboarding()` clears `hasOnboarded` without touching habits/logs/challenges (Settings dev tools). After hydration, an effect calls `scheduleAllReminders` whenever `notifications` or `habits` change, so reminder scheduling always reflects the latest preferences. Also exposes `debugBackfillLogs`, `debugAdvanceChallenge`, `debugCompleteChallenge`, and `resetAllData` — used only by the Settings developer tools section. `debugAdvanceChallenge` backfills all but the final day so the user can log the last day for real; `debugCompleteChallenge` backfills every day (including today) and sets the challenge straight to `'completed'`, for instantly previewing the post-completion state. `resetAllData` is local-only by design (sets a `skipNextDiffRef` flag) — it must never propagate as a mass-delete to a real Supabase account.
- [lib/habit-stats.ts](lib/habit-stats.ts) — a re-export barrel over [lib/domain/](lib/domain/) (see "Shared domain layer" below); every existing `@/lib/habit-stats` import (`streakForHabit`, `longestStreak`, `isDoneToday`, `recentHistory`, `consistency`, `challengeProgress`, `dayKey`, `addDays`, `totalCompletions`, etc.) keeps working unchanged. `challengeProgress` returns `{ habits: Habit[], ... }` (all habits in the challenge) and counts a day as complete only if **every** included habit was done that day (`allDoneOnDay`) — a habit that wasn't a Scheduled Opportunity that day (see below) can't be blamed for not being done, though every habit today defaults to daily/unpaused so this is currently a no-op. Keep these pure; Progress and Challenges screens depend on them producing identical answers from the same `(habits, logs, challenges)` triple.
- [lib/confirm.ts](lib/confirm.ts) — `confirmAction`/`alertMessage` wrap `Alert.alert`, falling back to `window.confirm`/`window.alert` on web (`react-native-web`'s `Alert.alert` is a no-op). Use these instead of `Alert.alert` directly for any destructive action or validation message, so it works in the web preview too.
- **The core loop** (in [app/(tabs)/index.tsx](app/(tabs)/index.tsx)'s `handleLog`): logging a habit fires `useCelebration()` ([lib/use-celebration.ts](lib/use-celebration.ts)), which triggers all three reward channels together — `expo-haptics` pulse, a synthesized chime via `useChime()` ([lib/use-chime.ts](lib/use-chime.ts), asset generated by [scripts/generate-chime.js](scripts/generate-chime.js)), and a particle-burst `<CelebrationOverlay>` ([components/celebration-overlay.tsx](components/celebration-overlay.tsx)). Challenge and multi-habit "all done" moments reuse the same primitives with `big: true`. Since Phase 3, `handleLog` also checks `isRecoveryEvent` ([lib/domain/recovery.ts](lib/domain/recovery.ts)) for the just-logged completion and, if true, fires a stronger recovery-specific celebration (`big: true`, copy from `docs/phase-3-experience-plan.md` §6.2) instead of the routine one — recovery is deliberately a stronger moment than a routine completion or a round-number milestone (every 25th Total Completions, routine strength, never `big: true`). Keep new reward triggers going through `useCelebration` rather than rolling bespoke animations.

### Shared domain layer (Phase 2 foundations)

[lib/domain/](lib/domain/) is the single source of truth for behavioural logic — per `docs/habit-tracker-evolution-plan.md`, no screen, Edge Function, notification service, or analytics layer may reimplement its own definition of a concept that lives here; add new behavioural metrics/signals here first, then consume them elsewhere.

- [lib/domain/day-key.ts](lib/domain/day-key.ts) — `dayKey`, `addDays`, `parseDayKeyParts`, `weekdayOf`, `localDayKeyOf`, `daysBetween`. Lowest-level date utilities with zero dependencies; `weekdayOf` is built on the local `Date(year, month-1, day)` constructor, never `new Date(dayKeyString)` (which JS parses as UTC midnight and can report the wrong weekday once converted back to local time).
- [lib/domain/habit-stats.ts](lib/domain/habit-stats.ts) — the pure functions re-exported by the `lib/habit-stats.ts` barrel above, including `totalCompletions(habitId, logs)` (Phase 3): the cumulative, never-resetting completion count, consolidating what was previously an inline `logs.filter(...)` pattern duplicated across screens.
- [lib/domain/schedule.ts](lib/domain/schedule.ts) — `HabitSchedulePeriod` (`lib/habit-types.ts`), `scheduleForDate`, `isScheduledOpportunity`, `scheduledOpportunitiesUpTo`. A habit's schedule/pause history is an append-only, effective-dated list of periods (no `effectiveTo` — the period governing a date is whichever has the greatest `effectiveFrom <= date`, so a schedule change never recalculates the meaning of past periods). A habit with zero periods (every habit today — there's no schedule-editing UI yet) resolves to daily/unpaused, identical to pre-Phase-2 behavior. No date before a habit's creation is ever a Scheduled Opportunity.
- [lib/domain/config.ts](lib/domain/config.ts) — `RECOVERY_CONFIG`/`MOMENTUM_CONFIG`, the one place every Recovery Rate and Momentum State threshold lives.
- [lib/domain/recovery.ts](lib/domain/recovery.ts) — `recoverableLapseInstances`, `recoveryEvents`, `closedLapses`, `averageRecoveryTime`, `recoveryRate` (returns both lifetime and rolling-window horizons together). Recovery Rate measures recovery on the *first available* Scheduled Opportunity after a miss (pairwise), so one long unbroken miss streak yields multiple resolved "not recovered" instances rather than one verdict — see the worked examples in `docs/phase-2-implementation-plan.md` section 3. Recovery Time is a deliberately coarser, whole-Lapse metric.
- [lib/domain/momentum.ts](lib/domain/momentum.ts) — `candidateStateAt` (raw, per-opportunity classification into one of 7 internal keys: `insufficient_data`, `building`, `steady`, `recovering`, `rebuilding`, `thriving`, `quiet`) and `confirmedStateAt` (the displayed value: a transition only takes effect once a new candidate has held for `MOMENTUM_CONFIG.transitionConfirmationOpportunities` consecutive opportunities, via the generic `computeConfirmedState` hysteresis helper). User-facing labels (Phase 3, `docs/phase-3-experience-plan.md` §7.1) are a presentation-only mapping kept in `app/(tabs)/progress.tsx`'s `MOMENTUM_COPY`, not in the domain layer: Getting started, Building momentum, Steady, Thriving, Recovering, Rebuilding, Quiet stretch — each a compact badge plus a one-line narrative, every label describing a stretch of time, never the person.
- Everything above is derived-on-read from `habits`/`habit_logs`/`habit_schedule_periods` — nothing is cached or event-sourced, so retroactive edits (a backfilled log, a backdated schedule change) correctly change every downstream calculation on the next read.
- **Wired into the UI as of Phase 3**: `app/(tabs)/progress.tsx` shows each habit's Momentum State badge + narrative, Recovery Rate (rolling) + Recovery Count, and Average Recovery Time; `app/habit/[id].tsx` shows a Recovery tile (Recovery Rate or Recovery Time, whichever the habit's display rules allow); `app/(tabs)/index.tsx` fires a stronger celebration on a Recovery Event. Momentum State and Recovery Rate are per-habit outputs with no cross-habit aggregate function — Progress's own top-of-screen summary is intentionally limited to the metrics that are safe to sum/average across habits (Total Completions, Consistency); it does not show a single blended Momentum State or Recovery Rate across multiple habits, since that would require inventing a new behavioural rule the domain layer doesn't define. Streaks are still computed (`streakForHabit`/`longestStreak`) but are now shown only in Habit Detail, folded into one tile beside Total Completions — never on Today or Progress. Habit Health and reflection/coaching-prompt facts remain unbuilt (Phase 5); notification copy and the challenge partial-credit redesign remain unbuilt (Phase 8 and 7 respectively).
- [scripts/build-edge-functions.js](scripts/build-edge-functions.js) regenerates a whitelisted subset of `lib/domain/day-key.ts` + `lib/domain/habit-stats.ts` into both Edge Functions (see "AI coaching" below) between `BEGIN/END GENERATED DOMAIN` marker comments, since the Edge Functions are hand-pasted into the Supabase Dashboard with no build step and can't do a live shared import. Run `npm run build:edge-functions` after changing either source file, then re-paste the regenerated function(s). The generator refuses to run if the shared domain layer picks up an `expo-*`/`react-native`/`@supabase/*`/`Deno.*` dependency.

### Auth & Supabase sync

- [lib/supabase.ts](lib/supabase.ts) — the Supabase client singleton, reading `EXPO_PUBLIC_SUPABASE_URL`/`EXPO_PUBLIC_SUPABASE_ANON_KEY` from `.env` (see `.env.example`). Auth tokens persist to `AsyncStorage`; an `AppState` listener starts/stops token auto-refresh on foreground/background.
- [lib/auth-store.tsx](lib/auth-store.tsx) — `AuthProvider` / `useAuth()`: wraps `supabase.auth`, exposes `{ session, user, initializing, signUp, signIn, signOut }`. Wraps `HabitStoreProvider` in [app/_layout.tsx](app/_layout.tsx), so the habit store can read the current `userId`.
- [lib/sync-queue.ts](lib/sync-queue.ts) — a persisted outbox in `AsyncStorage` (`enqueue`/`peekAll`/`dequeue`) of pending `{ table, op: 'upsert' | 'delete', payload }` operations, the unit of work pushed to Supabase.
- [lib/supabase-sync.ts](lib/supabase-sync.ts) — the only file that knows the Postgres row shapes (snake_case `habits`/`habit_logs`/`challenges`/`user_settings`, see [supabase/schema.sql](supabase/schema.sql)). `diffAndSync(prev, next, userId)` compares two `HabitState` snapshots and enqueues the minimal ops, then calls `pushPendingChanges()` — called from a `habit-store.tsx` effect on every state change, which is how mutators stay backend-agnostic. `pullRemoteChanges(userId)` fetches rows changed since a per-user watermark and merges them in last-write-wins by `updatedAt`; `deleted_at` tombstones (habits/challenges are soft-deleted) drive removal — `habit_logs` rows are hard-deleted instead since they're leaf records with no children, so cross-device propagation of an "uncheck" is best-effort rather than guaranteed. `enqueueFullUpload` is the one-time legacy-data-migration upload described above. There's no realtime subscription — pulls happen on sign-in and on every app foreground, which is enough for a personal habit tracker without the complexity of a live multi-device feed.
- [supabase/schema.sql](supabase/schema.sql) — run once in the Supabase SQL Editor. All tables use `text` primary keys (not Postgres `uuid`) so client-generated IDs (`expo-crypto`'s `Crypto.randomUUID()`) pass through unchanged, and all four tables have row-level security scoped to `auth.uid() = user_id`.
- [supabase/habit_schedule_periods_schema.sql](supabase/habit_schedule_periods_schema.sql) — run once alongside the main schema. Backs `HabitState.schedulePeriods` (see "Shared domain layer" above); purely additive, and empty for every habit until a schedule-editing UI ships in a later phase.

### AI coaching (Claude via a Supabase Edge Function)

- [supabase/ai_insights_schema.sql](supabase/ai_insights_schema.sql) — the `ai_insights` table (`kind`: `'nudge' | 'weekly_reflection' | 'monthly_reflection'`, `content`, `period_start`/`period_end`, RLS scoped to `auth.uid() = user_id`), run once in the SQL Editor alongside the main schema.
- [supabase/functions/ai-insights/index.ts](supabase/functions/ai-insights/index.ts) — a Deno Edge Function (pasted into Dashboard → Edge Functions, not deployed via CLI) invoked with `{ kind: 'nudge' | 'weekly' | 'monthly' }`. It's the only place the Anthropic API key (a Supabase secret, never sent to the client) is used. Builds a **user-scoped** Supabase client from the caller's forwarded JWT (anon key + `Authorization` header) — every DB read/write inside the function goes through RLS, no service-role key needed. Checks `ai_insights` for a fresh-enough row first (nudge: ~20h, weekly: ~7d, monthly: ~30d) and returns it without calling Claude if found — this is the only rate limiting / cost control, and it's sufficient at this app's scale. On a cache miss, pulls `habits`/`habit_logs` for the relevant window, maps the raw snake_case rows to the shared domain shape (`toDomainHabit`/`toDomainLogs`, mirroring `lib/supabase-sync.ts`'s client-side row mapping) and computes per-habit streak/consistency using the *generated* block between `BEGIN/END GENERATED DOMAIN` markers (see "Shared domain layer" above — no longer a hand-duplicated reimplementation), then calls `claude-sonnet-4-6` via `npm:@anthropic-ai/sdk` (Deno's native npm specifier, no bundler) with a short system prompt per `kind` and no extended thinking (these are generation-from-stats tasks, not reasoning tasks).
- [lib/ai-coach.ts](lib/ai-coach.ts) — `getInsight(kind)` wraps `supabase.functions.invoke('ai-insights', ...)`, returning `null` on any failure (network, missing secret, etc.) so a broken AI call never breaks the Progress screen — this is supplementary content, not core habit data.
- [app/(tabs)/progress.tsx](app/(tabs)/progress.tsx) — a "🧠 Coach" card above the existing 14-day/7-day toggle, fetched on mount when `habits.length > 0`: the latest nudge, plus a separate This week / This month toggle for the longer reflection (independent of the existing 14/7-day toggle, which drives the per-habit heatmaps below it).

### Notifications (retention hook)

[lib/notifications.ts](lib/notifications.ts) wraps `expo-notifications` to schedule **locally-scheduled daily reminders** (`SchedulableTriggerInputTypes.DAILY`) — there is no backend, so this is not remote push. `scheduleAllReminders(notifications, habits)` cancels everything and reschedules: one reminder per global check-in time in `notifications.times`, plus one per `habit.reminderTimes` entry (with habit-specific copy). It's called automatically from `lib/habit-store.tsx`'s post-hydration effect, not from screens directly. `notificationsSupported` is `false` on web (expo-notifications has no scheduling backend there) — `scheduleAllReminders` and `ensureNotificationPermission` no-op/return safely on web rather than throwing, so preferences still save and the Settings toggle stays usable; reminders only actually fire on an iOS/Android dev or production build. Remote push notifications are not supported in Expo Go on Android (post-SDK-53), and local notification delivery in Expo Go can be unreliable.

### Theming

Colors are centralized in [constants/theme.ts](constants/theme.ts) as a `Colors.light` / `Colors.dark` map (keys: `text`, `background`, `tint`, `icon`, `tabIconDefault`, `tabIconSelected`), plus a `Fonts` map keyed per-platform (`ios` / `default` / `web`).

Don't read `useColorScheme()` and index into `Colors` directly in screens — use the themed primitives, which already resolve the right color and support `lightColor`/`darkColor` overrides:
- [components/themed-text.tsx](components/themed-text.tsx) / [components/themed-view.tsx](components/themed-view.tsx) — themed `Text`/`View` wrappers
- [hooks/use-theme-color.ts](hooks/use-theme-color.ts) — resolves a color name through `Colors[scheme]`, with optional per-call overrides
- [hooks/use-color-scheme.ts](hooks/use-color-scheme.ts) / `.web.ts` — platform-specific color scheme hooks (the web variant defers to client hydration to support static rendering)

## Compatibility note

The app is pinned to **Expo SDK 54** specifically because the locally installed Expo Go client only supports SDK 54 — the public Expo Go release lags behind the npm `latest` tag (currently SDK 56). If you bump the `expo` package, the project must be regenerated from the matching `expo-template-default@sdk-XX` template rather than patched in place — `npx expo install --fix` on a manually-bumped `expo` version produces unresolvable peer-dependency conflicts (e.g. `expo-router` pinned to a different SDK line than `expo`). Check the Expo Go client version on the test device before changing SDKs.
